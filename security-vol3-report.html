🔴 漏洞详情

ATK-W01 CRITICAL 已修复
设备白名单完全绕过
_checkDangerousAction() 中，白名单检查逻辑为 if (deviceId != null && !whitelist.isAllowed(deviceId))。 如果请求不包含 x-device-id 头，整个白名单检查被直接跳过。 攻击者只需不发送此头即可绕过整个设备配对机制。
// 漏洞代码 final deviceId = req.headers.value('x-device-id'); if (deviceId != null && !_whitelist.isAllowed(deviceId, ...)) { // 拒绝 } // deviceId == null → 跳过！白名单形同虚设
修复：deviceId 现在是必填字段。未提供 x-device-id → 直接 403 Forbidden。
新增审计日志 NO_DEVICE_ID 记录此类攻击。
ATK-W02 HIGH 已修复
test-mode 生产后门
/audit-log 端点允许 x-test-mode 请求头绕过认证。 任何知道此头的攻击者无需 Token 即可读取全部审计日志，获取其他 IP 的请求记录、SAFE_MODE 状态等敏感信息。
// 漏洞代码 void _handleAuditLogRequest(HttpRequest req) { if (!_isAuthorized(req) && !_isTestMode(req)) { // ← test-mode 绕过！ _respondForbidden(req, 'Unauthorized'); return; } // ...返回审计日志 }
修复：移除 /audit-log 中的 _isTestMode() 绕过。 x-test-mode 仅保留在 SAFE_MODE 分支（合理使用场景：测试安全拦截效果而不真正执行）。
ATK-W03 HIGH 已修复
未授权信息泄露
三个端点无需认证即可访问：
  • /safe-mode — 泄露 SAFE_MODE 开关状态（攻击者据此判断能否执行危险指令）
  • /heartbeat — 泄露时间戳 + SAFE_MODE 状态
  • /ping — 确认服务存活（风险较低，保留用于发现）
攻击者可先访问 /safe-mode 确认 SAFE_MODE=OFF，再发起关机等攻击。
修复：
  • /safe-mode 现在需要认证（或 test-mode）
  • /heartbeat 不再泄露 timestamp 和 safeMode，仅返回 {"status":"alive"}
  • /ping 保留用于服务发现，但精简为仅 {"status":"alive"}
ATK-W04 MEDIUM 已修复
无 CORS / 安全响应头
HTTP 响应没有任何 CORS 限制或安全头，攻击场景：
  1. 用户在浏览器打开恶意网页
  2. 网页 JS 向 http://局域网IP:9998/shutdown 发送 POST
  3. 如果浏览器有用户的认证 Cookie（本应用不用 Cookie，但未来可能加）
  4. 跨域请求成功 → 电脑关机
此外缺少 X-Frame-Options（点击劫持）、X-Content-Type-Options（MIME 嗅探）等安全头。
修复：添加完整安全响应头：
  • CORS：仅允许 localhost 来源（4 个白名单 URL）
  • X-Frame-Options: DENY — 防点击劫持
  • X-Content-Type-Options: nosniff — 防 MIME 嗅探
  • X-XSS-Protection: 1; mode=block — 防 XSS
  • Cache-Control: no-store — 防敏感响应被缓存
  • OPTIONS 预检 — 正确处理 CORS preflight
ATK-W05 MEDIUM 已修复
速率限制内存泄漏
_rateLimit Map 中，只失败 1-2 次的 IP 记录永远不会被清理。 长期运行后（尤其是暴露在公网），Map 会持续增长导致内存泄漏。 成功的 IP 会被 _recordSuccess() 移除，但部分失败的永远残留。
修复：添加定期清理机制：
  • 每 5 分钟或记录超过 100 条时触发清理
  • 移除：已过期的封禁记录 + 未封禁但失败未达阈值的记录
  • 防止 _rateLimit 无限增长
